# Universal booking backend

The universal engine extends existing documents without renaming or deleting legacy fields.
No destructive migration is required.

## Booking document (schema version 2)

New bookings keep `propertyId`, `inspectionDate`, `inspectionTime`, `guestPhone`, `status`,
`paymentStatus`, and `reminderSent` for compatibility. They also store:

- `listingId`: alias of `propertyId` for future listing terminology.
- `bookingMode`: inspection, vehicle, event, horse, or generic mode.
- `listingCategory`: listing type captured when the booking is created.
- `startAt` and `endAt`: canonical Firestore timestamps.
- `durationMinutes`, `quantity`, `pricingUnit`, and `estimatedTotal`.
- `categoryDetails`: allow-listed optional details only.
- `requestId`: idempotency key generated by the client.
- `schemaVersion`: currently `2`.

Readers default old documents to `property_inspection`, derive `startAt` from the legacy
inspection date/time, and use a 30-minute duration when no duration was stored.

## Availability and conflict safety

`getBookingAvailability` returns sanitized schedule blocks without customer IDs, phone numbers,
notes, or payment details. `createUniversalBooking` re-reads the listing and every active booking
for that listing in a Firestore transaction before writing. Direct client booking creation is
disabled in `firestore.rules`.

Listings may optionally store `availabilityConfig`. It supports multiple agent schedules,
working days and hours, slot intervals, booking duration, per-day limits, unavailable dates,
vacation periods, listing-wide blocked dates, buffers, and minimum duration. Existing listings
without this field retain the Monday-Saturday, 9:00 AM-5:00 PM default inspection schedule.

The callable rejects stale slots, overlapping ranges, duplicate inspection requests, unavailable
listings, invalid date ranges, unsupported times, and duplicate submissions. Its deterministic
document ID makes retries idempotent.

## Payments

Inspection bookings continue to use `inspection_fee`. Other modes use `booking_payment`, which
must reference a booking owned by the payer. Firestore rules and `verifyPaystackPayment` both
require the payment amount to equal the booking's stored `estimatedTotal`. Successful Paystack
verification updates the related booking's `paymentStatus`.

## Reminders

The existing callable and scheduled scan names remain unchanged for compatibility. They now read
`startAt` when present, fall back to legacy inspection fields, and build mode-specific reminder
copy from the shared configuration.

## Deployment order

Deploy Functions and Firestore rules together so the callable write path is live when direct
client booking creation is disabled:

```powershell
corepack pnpm dlx firebase-tools@13.35.1 deploy --only functions,firestore:rules,firestore:indexes
```

Run the local checks first:

```powershell
npm run build
npm --prefix functions test
```
